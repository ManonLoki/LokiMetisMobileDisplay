## 为什么这样分层

整个系统按“谁最可信、谁最受限”来分工：

| 层 | 承担什么 | 为什么放在这里 |
| --- | --- | --- |
| 桌面（Rust） | 统计 Token、读取额度、产生 Hooks；提供主连接的配对、认证与会话加密核心 | 桌面为数据源；Android、Desktop 与 iOS 主 App 链接同一份 Rust 主连接协议实现 |
| Desktop 展示 App | 接收采集端完整快照与图片，使用 Android 平板样式的窗口界面 | 实验终端只负责展示；窗口存续期间维持连接，使用现有 Android 平板协议身份 |
| iPhone App | 在 Apple 产品中持有主配对秘密；认证、接收完整快照与图片；分发给 Watch 和小组件 | 前台维护实时连接，后台由系统批准短时刷新；私有 Keychain 与 App Group 分开管理 |
| Watch | 显示、本机缓存；iPhone 不可达时用只读 HTTP 自取摘要 | 仅持独立只读密钥与展示缓存，不持主配对秘密，不维护桌面 TCP 长连接 |
| 小组件 | 显示最近一次摘要；系统唤醒时短时 HTTP 刷新 | 按系统预算执行一次有界刷新，不建立主连接或进行配对 |

由此得出一条贯穿全局的原则：**能力向下逐级收窄**。iPhone 拿到的是完整权限，Watch 和小组件只拿到“只读摘要”的独立密钥；该权限不能通过摘要端点获取配对秘密、Hook 正文或图片。这里限制的是 HTTP 权限范围；iPhone 向 Watch 发送的完整快照与图片另走系统配套通道，App Group 也包含供主 App 恢复的完整展示缓存。

Apple 端的 Codable 数据编解码、文件事务、网络与 Watch 通道适配放在 `appleDisplay`：Xcode 的 App、Watch、小组件 target 按需直接编译这些 Swift 源码，并分别链接对应平台的 `SharedLogic.framework`。SwiftPM（Swift 包管理工具）测试实际链接 `macosArm64` Kotlin 框架；统一入口 `python3 scripts/test_apple_shared.py` 会先构建框架再执行测试。Swift 侧保留系统适配，共用业务规则由 Kotlin 实现。

## 共享规则与平台实现

当前采用“共享业务规则、按实际消费者共享界面”的 KMP 分工。`androidApp` 和 `desktopApp` 均依赖 `sharedUI` 与 `sharedLogic`；`sharedUI → sharedLogic`。iPhone／iPad、Watch 与 iOS 小组件保留 SwiftUI 并实际链接 `SharedLogic.framework`。实验分支新增 Desktop 后，五份 Compose 通用界面文件从 Android 抽入 `sharedUI/commonMain`，系统入口、图片与设置动作由应用注入。

| 位置 | 当前职责 | 调用范围 |
| --- | --- | --- |
| `sharedLogic/commonMain/domain` | 完整／摘要使用的快照和额度模型、语义校验；面板默认值、配置恢复、列数和分页 | Android、Desktop 与 Apple 实际调用；Swift 保留 Codable 字段映射，校验交共享模型 |
| `sharedLogic/commonMain/protocol` | 名称与能力校验、连接阶段／期限、最多 8 次退避重试、形态上报、帧容量／长度、写队列、Watch 前台租约／通信事实／传输选择／块边界、JSON 边界、主 LAN／Watch 图片引用与候选、只读 HTTP 请求与响应及局域网地址边界 | Android、Desktop 与 iPhone 共享主连接规则；Apple 各目标按功能调用 Watch 规则，系统传输与字节缓冲留在平台 |
| `sharedLogic/commonMain/presentation` | Agent 别名、启用过滤、排序、Token／额度行合并、Cursor 默认零行、数字格式化、摘要裁剪、图片解码预算 | Android、Desktop、iPhone、Watch 与小组件按各自界面调用共享规则；图片系统解码器留在平台 |
| `sharedLogic/commonMain/storage` | 来源与接收时间接纳、同时间完整度优先、历史图片／清除事实、图片淘汰资格与预算、旧 HTTP 拒绝、租约、刷新判断、读取凭据身份比较、配对索引身份恢复、Watch HTTP 配置修订／撤销／去重／缓存保留 | Android 与 Apple 按实际功能在本地锁或文件事务中调用；不包含磁盘或密钥库访问 |
| `sharedLogic/androidMain` | NSD、TCP、Keystore、文件缓存、小组件 HTTP、JNI | 仅 Android；按 `connection`、`storage`、`widget`、`nativebridge`、`protocol` 分目录 |
| `sharedLogic/appleMain` | Foundation Unicode NFC 适配，供各 Apple 目标复用相同的名称比较语义 | 保留原文，只规范化比较键；Android 使用系统 Normalizer |
| `sharedLogic/desktopMain` | JVM Unicode NFC 适配 | Desktop JVM；系统 Normalizer |
| `sharedUI/commonMain` | 展示台、设置、用量卡片、Hooks 图文详情与动效 | Android 与 Desktop 共用；平台图片、时间格式和动作由入口注入 |
| `androidApp` | 权限、应用生命周期、平台界面、前台服务、悬浮窗、系统小组件和刷新调度 | 仅 Android |
| `desktopApp` | JVM 窗口、mDNS、Selector TCP、Rust JNI、私有文件、Skia 图片与宿主打包 | macOS／Windows／Linux 构建配置，本次只验证 macOS arm64 |
| `iosApp` 与 `appleDisplay` | SwiftUI、Network.framework、Keychain、App Group、WatchConnectivity、WidgetKit | 按 Apple target 的权限与生命周期分别执行 |

表中的 `commonMain`、`androidMain` 是源码集合；实际文件在对应集合的 `kotlin/com/manonloki/lokimetrisdisplay/` 下分目录。目录分层保留原 Kotlin package，避免改变 JNI 入口及 Swift 导出 API。网络 owner、线程和系统后台资格仍归各平台，不因共用策略而变成同一个跨平台常驻服务。

`TerminalWidgetSnapshot` 从原 Android 摘要类提取到共享层，负责从合法快照裁剪正文、图片与资源清单，以及验证裁剪结果。Apple 保留既有 Codable 摘要和缓存字段，将值映射到共享模型进行校验。Swift 与 Kotlin 的整数转换先检查范围或确保越界值仍被拒绝，非法输入通过结果值或 Swift 自身错误处理，不依靠未声明的 Kotlin 异常跨语言传播。

Android 主面板与 Apple 各界面调用共享的 K/M/B 缩写和精确整数分组；Android 桌面小组件调用同一 `TokenFormatting` 的 K/M/B/T/P/E 入口，保留原有单位策略。共用规则不改变各端原有持久化字段：平台继续负责文件版本、原子提交、密钥库、系统调度和刷新间隔。

展示策略直接通过 `UsageDisplayPolicy` 和快照的 `displayUsageRows` 调用。没有生产消费者的顶层转发与旧展示入口已删除；Swift Codable 外壳和实际使用的 UI／错误适配继续保留，测试覆盖生产投影或共享策略本身。

Apple 摘要存储只保留认证提交、心跳续期和 HTTP 接纳等实际生产入口。旧独立目标写入与无条件摘要写入已移除；测试通过真实认证事务建立状态，专门的进程中断盘面由测试夹具构造，不向生产模块恢复旁路写 API。

Apple 构建目标包含 iOS arm64 真机／arm64 模拟器、watchOS arm64_32 与 arm64 真机／arm64 模拟器；`macosArm64` 用于 Apple Silicon 本机测试。Xcode 各 target 统一调用 `python3 scripts/build_apple_shared.py`，通过进程锁串行构建对应框架。Desktop JVM 使用 `jvm("desktop")` 目标，和用于 Swift 测试的 `macosArm64` 原生框架分开。Rust 配对桥随 Android、Desktop 与 iPhone／iPad 主 App 构建和链接，Watch、小组件的只读 HTTP 加密使用系统实现。

## 端到端数据流

### 1. 发现与配对（首次）

```
iPhone 前台                                 桌面
  │  NWBrowser 浏览 _loki-host._tcp.local.    │
  │◀──────────── Bonjour 广告（只作候选，不授信）│
  │  用户点“配对” → Rust 开配对窗口，生成四位码 │
  │──── TCP：pairHello ─────────────────────▶│  桌面弹窗，用户输入四位码
  │◀─── reply ───────────────────────────────│
  │──── confirmation ───────────────────────▶│
  │  Rust 返回配对材料 → 写 Keychain → 读回成功 │
  │──── ack（只有 Keychain 真正保存后才发） ──▶│
  │  关闭这条 socket，另开新连接走认证          │
```

主 App 展示的四位码来自 Rust 配对窗口；桌面端用户确认后才建立配对。共享 `TerminalSessionTimingPolicy` 给出 60 秒的宿主期限，Rust 另管理配对密码预算和尝试次数；Swift 侧的网络重试不重开窗口或返还尝试次数。桌面端内部实现不属于本仓库，本篇不把广告内容当作配对凭据。

### 2. 认证与实时同步（之后每次）

```
iPhone                                       桌面
  │── resume introduction（用保存的秘密）───▶│
  │◀── resumeReply ─────────────────────────│
  │── confirmation ────────────────────────▶│
  │── 加密的设备信息（名称、平台、版本）─────▶│
  │◀── snapshot（完整快照）──────────────────│  收到第一份快照才显示“已连接”
  │◀── ping ─▶ pong（桌面定期发送；45 秒没有任何入站消息即判断线）
  │── assetRequest(hash, offset) ──────────▶│  一次只请求一张图的一个 16KiB 块
  │◀── assetChunk ──────────────────────────│
```

主 App 的局域网会话加密、序号和资源完整性检查由 Rust 完成（`NativeLinkBridge.call`）。Swift 按 Rust 给的阶段收发帧，并在任何异常时**关闭 socket 换新连接**——已经消耗的加密序号绝不在同一连接上重发；连接选择与重试预算由共享 Kotlin 策略维护。

`TerminalFramePolicy` 统一长度前缀后的正文边界、单次最多 16KiB 读取与累计缓冲容量；`TerminalWritePolicy` 统一包含在途帧的 8 项写队列和 2 秒写期限。握手帧上限 4096 字节，业务密文帧上限 98304 字节。Android 保留 ByteBuffer／ByteArray，Apple 保留 Data 和系统完成回调，容量判断只传数值，不把大块网络缓冲搬到另一语言。

### 3. 快照到达之后的扇出

```
             ┌─▶ 主线程界面（LanLinkView，内容未变则不投递）
             │
认证快照 ────┼─▶ WidgetSnapshotPublisher ─▶ App Group（摘要 + 完整展示缓存）─▶ 小组件刷新（内容变化立即请求；相同投影30秒节流）
             │
             ├─▶ 图片：缓存命中？ ─是─▶ 解码队列 ─▶ 界面
             │                   └否─▶ 逐块下载 → Rust 校验 → 原子落盘 → 解码队列
             │
             └─▶ PhoneWatchBridge ─▶ Watch（快照 + 已落盘图片，逐块确认）
```

快照中的可选 `enabledAgents` 表示桌面设置中完整的 Agent 启用名单，不从用量明细或 Hooks 反推。字段缺失或为 `null` 时兼容旧桌面；空数组表示明确全部关闭。各端按名单生成可见用量行与额度列表，保留桌面给出的总量、质量和时间。名单随 HTTP 摘要、缓存及 Watch 快照传递，避免重启或后台刷新后重新出现已关闭的账户。

### 4. iPhone → Watch

Watch 通道用 `sendMessageData` 即时 RPC 传输快照与图片，不用系统后台文件队列（避免无法撤销的排队传输）。另外通过 `updateApplicationContext` 下发只读 HTTP 配置、缓存撤销标记，以及容量允许时的最近快照缓存；上下文超过 32KiB 时只发送配置与撤销标记，大快照由即时 RPC 分块补齐。

| 操作 | 方向 | 作用 |
| --- | --- | --- |
| `probe` | 手机→表 | 确认 Watch 前台在线，取回其前台代次与已持有的快照摘要 |
| `snapshotBegin` / `snapshotChunk` | 手机→表 | 分块传快照（每块 16KiB，单 RPC 不超过 32KiB，快照总量不超过 96KiB） |
| `assetBegin` / `assetChunk` | 手机→表 | 分块传图片；Watch 已有同摘要文件则直接回复 `cached` |
| `requestSync` | 表→手机 | Watch 主动要最新缓存；手机即使不在前台也能回复 |
| `pause` | 双向 | 通知对方本次前台代次已结束 |

关键约束：

- **单物理槽**：任何时刻只有一个 RPC 在途。超时（8 秒）只撤销逻辑资格，系统回调真正结束前不发第二个，防止系统内部无限排队。
- **先补图，后发新快照**：已提交清单里还缺的图片优先传完，持续变化的用量更新不能把大图“饿死”（共享 `WatchTransferRules`，Swift 保留 `WatchTransferPolicy` 负载枚举映射）。
- **租约**：两端各自记录最近一次真实通信时间，45 秒内才算可达；Watch 前台与系统允许的后台刷新窗口都可接收即时分块及 ACK。手机每 15 秒发一次 `probe` 续约，系统的 `isReachable` 只作为“可以尝试”的前提，不作为在线证明。

`WatchCommunicationPolicy` 维护前台代次、45 秒租约、真实 ACK 序号和完整同步事实；普通分块回执只更新通信，不伪造完整同步。报告年龄向上取整到毫秒，超过七天的事实省略。Swift 的 UInt64（64 位无符号整数）纳秒时间通过高低位完整传入共享层，在 Kotlin 内部使用无符号整数比较；状态不可变，复制给另一 owner 的事实快照不会被后续 ACK 修改。`WatchProtocolRules` 负责元信息、RPC 操作／状态及精确块偏移／块长校验，Swift 继续组装原始 Data、核对 SHA-256、编解码 JSON 并调用 WatchConnectivity。

### 5. Watch 的后备路径

```
Watch 前台 / 后台刷新
  │
  ├─ iPhone 可达？──是─▶ requestSync ─▶ 收到缓存或等待分块（最多 8 秒）
  │                                     └─ 超时或无进展 ─┐
  └─ 否 ─────────────────────────────────────────────────┴▶ 只读 HTTP 向桌面取摘要（15 秒内最多一次）
```

HTTP 只返回 Token、额度和 Hooks 四态，不含正文和图片；Watch 会按共享历史图片规则保留同一插槽、同一 Agent 之前的合法图片关联。Watch 的 Hooks 界面只展示 Agent、四态和图片，没有正文或详情页；传输模型仍复用含正文兼容字段的完整快照，界面限制不等于传输字段已被删除。

下发 HTTP 配置的 `WatchConfigurationPolicy` 统一修订接纳、显式撤销、重复消息去重和缓存保留。跨语言边界把修订号表示为规范 u64 十进制字符串，Swift Codable 仍保留 UInt64 字段；同手机只接受更高修订或完全相同的重送，同号内容冲突与旧消息不能恢复撤销授权。新修订先持久提交再发布，u64 耗尽时拒绝递增。规则还决定哪些同手机、同来源的缓存或在途作业可以保留；撤销 HTTP 权限可以保留相容的已验证展示缓存，但缓存不能恢复读取授权。Keychain、配置字节编码及系统发布继续由 Swift 负责。

Android 与 Apple 的只读 HTTP 客户端共同调用 `WidgetHttpPolicy`，统一固定路径、6 秒期限、96KiB 响应容量、响应来源与类型、重定向和 nonce（每次请求的随机值）边界，以及绑定请求 nonce 的附加认证数据。平台继续组装 URL／JSON、执行 Base64 解码和密码运算、按流限制实际字节；Android 原有 1KiB 请求上限与规范 Base64 要求、Apple 原有响应 Base64 接纳方式保留。`WidgetEndpointRules` 共用严格 IPv4、scope（IPv6 接口作用域标识）与已解析地址字节分类；IPv6 解析继续由系统执行，Apple 的 `.local` 与构造时小写化、Android 的数值对端约束保持原样。

### 6. 后台刷新

| 端 | 机制 | 间隔 | 做什么 |
| --- | --- | --- | --- |
| iPhone | `BGAppRefreshTask` | 申请最早 5 分钟后，由系统决定 | 用保存的 Bonjour 服务名重新解析地址，认证，收一份快照写入 App Group 后结束；不下载图片，25 秒本地超时 |
| 小组件 | Timeline `.after(5 分钟)` | 同上 | 摘要仍在 45 秒租约内则读缓存以抑制重复 HTTP；App 心跳可续租，HTTP 新摘要也有初始租约；否则尝试一次只读 HTTP |
| Watch | `scheduleBackgroundRefresh` | 申请 5 分钟后 | 先读手机上下文与缓存，不可达再 HTTP，12 秒预算 |

## 线程与队列模型

网络与 Watch 会话状态由各自 owner 的串行队列管理，主线程接收不可变的“投影”。跨队列投递、共享发布器的提交入口和系统完成回调另用锁协调；App Group 事务还需要跨进程文件锁。耗时图片解码交给独立队列，结果回 owner 后再次检查代次与引用。

| 队列 | 所属 | 负责 | 不做什么 |
| --- | --- | --- | --- |
| 主线程 | SwiftUI、`LanLinkModel`、`WatchLinkModel` | 渲染、把投影赋给 `@Published`、处理 UI 与系统调度入口 | 不在渲染与投影路径执行网络、图片解码或整文件校验；设备设置初始化另有 Keychain 访问 |
| `LokiMetris.lan-link` | `LanLinkEngine` | Bonjour、TCP、Rust 调用、Keychain、图片分块写盘、1 秒期限检查 | 不做多帧解码与冷启动整文件校验 |
| `LokiMetris.lan-decode`（utility） | `LanLinkEngine.decoder` | 图片校验与解码，结果回投网络队列 | 不碰引擎状态 |
| `LokiMetris.phone-watch` | `PhoneWatchBridge` | WCSession 回调、分块传输、配置下发、15 秒心跳 | — |
| `LokiMetris.widget-snapshot` | `WidgetSnapshotPublisher` | App Group 写入（跨进程文件锁）、`reloadTimelines` | — |
| `LokiMetris.watch-link` | `WatchLinkEngine` | WCSession 回调、分块接收、本机缓存、HTTP 结果处理 | 不做解码 |
| `LokiMetris.watch-decode`（utility） | `WatchLinkEngine.decoder` | Watch 图片解码 | 不碰引擎状态 |

**LAN／Watch owner → 主线程的状态投递**使用 `LanProjectionDelivery`：只保留最新一份值和最多一个待执行任务，主线程慢的时候中间状态直接被覆盖，不会积压。再加上引擎侧“与上次投递相同则跳过”，心跳、分块回执这类未改变投影的事件不会因此额外投递界面更新（见 [04 · 性能优化](04-问题与技术路线.md#四本轮-ioswatch-性能与耗电优化)）。

**迟到回调的处理**：每次重连、切换桌面都递增 `generation`；所有异步回调都带着发起时的代次，回来时不一致就直接丢弃。Watch 侧对应的是 `foregroundGeneration`、`phoneRevision` 和 `httpAttempt`。

## 连接状态机

Android、Desktop 与 iPhone 使用共享 `TerminalSessionPhase`；iOS 的 `LanLinkEngine.Phase` 是它的类型别名。它描述当前这条 socket 处于协议的哪一步：

```
idle ─(首次配对)─▶ pairHello ─▶ pairConfirmation ─▶ pairClose ─▶ idle ─(另开连接)─┐
  └─(已配对)──────────────────────────────────────────────────────────────────▶ resumeReply ─▶ metadata ─▶ streaming
                                                                                         streaming ─(退后台)─▶ pausing ─▶ idle
```

- `TerminalSessionTimingPolicy` 统一配对 60 秒、握手／首次快照 15 秒、配对收尾 3 秒、入站空闲 45 秒、单块图片 10 秒的预算及到期原因优先级。平台 owner 读取本机单调时钟并执行资源清理；iOS 用 1 秒计时器检查，没有连接也没有期限时挂起。
- 失败分两类：**传输失败**（断网、超时）在新 socket 上有界重试，最多 8 次、退避 0.5～8 秒；**协议／认证失败**不重试，保留配对让用户决定是否忘记后重配。Android、Desktop 与 iPhone 主 App 共享 `TerminalConnectionPolicy` 的选择与退避规则，调度和 socket 执行分别留在平台 owner。

首次快照的预算起点保留平台差异：iOS 沿用 `connect` 开始的握手期限，Android 与 Desktop 在认证确认的写入完成回调中重新开始 15 秒预算。共同阶段和预算值不代表这一平台差异已被消除。

`TerminalCapabilities` 共用有界能力表和产品能力名；缺失字段映射为空表，坏类型或畸形表不能授予新能力。拒绝快照与撤销已有 HTTP 目标是不同动作，各入口的执行顺序仍有差异：

- Android 实时入口先严格校验能力表，再调用 `AndroidWidgetStore.acceptLive`。坏表会拒绝整份快照并关闭会话，尚未进入存储提交，原有小组件摘要及 HTTP 目标保留。
- Apple 主 App 先计算 HTTP 目标并调用 `watch.configureHTTP`，坏表得出空目标，先发起 Watch HTTP 配置撤销。前台随后严格校验并拒绝坏表快照，未调用共享发布器，因此 App Group 的已有 HTTP 目标保留；Watch 撤销实际送达仍依赖系统。
- Apple 系统后台刷新不经过该前台严格能力校验；快照本身合法时可带空 HTTP 目标进入认证提交，提交阶段移除 App Group 的旧目标，同时可保存合法摘要。合法能力表未声明 HTTP 能力或端点无效时，只有实际走到带空目标的提交入口，才会移除对应持久目标。

## 缓存与“谁更新”的判定

iPhone 实时快照、iPhone 后台刷新与小组件 HTTP 摘要写入同一个 App Group 缓存，必须有一致的“新旧”规则，否则旧数据会覆盖新数据。Watch 接收的手机数据和自行获取的 HTTP 摘要写入 Watch 本机缓存，不访问 iPhone 的 App Group。

App Group 缓存按以下规则合并；来源、时间、同时间完整度与 HTTP 接纳判断通过 `SnapshotAcceptancePolicy` 调用共享层，实际加锁、读写和原子替换仍在 Swift：

1. **同一来源才比较**；换桌面直接清空。
2. **按真实接收时间**（`phoneReceivedAtMs`）比较，晚的赢。
3. **时间相同按完整度**：完整快照（优先级 2）> 带历史图片或清除事实的摘要投影（1）> 纯摘要（0）。
4. **HTTP 只更新状态，不清图**：同一插槽、同一 Agent 的已缓存图片关联继续保留，并记录图片自己的接收时间；插槽换了 Agent 或完整快照明确清图时才移除。

iPhone 的图片字节保存在私有目录（按 SHA-256 命名），App Group 展示缓存只记录资源清单；Watch 收到的图片另存本表缓存。缓存接纳核对长度、格式魔数与摘要；`IOSDisplayCache` 对文件系统身份未变化的已验证文件复用校验结果，避免每次给 Watch 同步都整文件哈希。

`HookImageCachePolicy` 维护手机与 Watch 的历史图片选择、清除墓碑（记录插槽图片被明确清空的时间）和完整度优先级。相同手机、相同来源且时间未倒退的摘要才可复用历史图；插槽换 Agent、明确清图或同时间已有清除记录时，旧图片不能重新出现。共享层只处理槽位、Agent、图片摘要及时间等事实，Swift 按决定映射原有 Hook 和资源描述，文件路径与图片字节不进入规则对象。

`AssetTransferRules` 共用主 LAN 与 Watch 的完整描述／引用资格，主 LAN 候选按原清单顺序返回索引。Android 排除已解码与失败图片，iOS 还排除正在异步解码的图片；两端仍在下一块到达后才取消失效资源，各自执行缓存优先查找、解码和网络发送。Watch 图片块与快照块复用有界精确偏移规则，仍分别限制为 32MiB 和 96KiB。

`ImageCachePolicy` 共用受保护文件的排除、按宿主原有访问时间精度排序和容量核算；只有文件实际删除成功才扣除占用。Android、Desktop、iPhone 与 Watch 都以 512 MiB 为淘汰目标，Android、Desktop 与 Watch 另以 512 文件为目标，iPhone 不限制文件数。当前快照引用的文件受保护；引用文件本身超过预算或删除失败时，目录可以超过目标，这些数值不是磁盘硬上限。目录扫描、符号链接检查、文件删除及失败处理仍在平台。

`ImageDecodePolicy` 共用源图片像素边界、目标尺寸及 Apple 逐帧预算与缩边判断。Android 仍使用系统解码器并沿用原有逐图缩放；Apple 仍使用 ImageIO 读取帧信息并核算真实行字节，保留全部动画帧。共享预算不把图片或像素缓冲传入 Kotlin。

摘要的 45 秒租约与是否需要刷新由 `SnapshotFreshnessPolicy` 判断。Apple 主 App 认证快照与 HTTP 认证摘要均创建初始租约，主 App 的活跃连接心跳可续租；读取缓存本身不续租。小组件仅用它抑制重复 HTTP，不将其作为 UI 实时在线证明；租约到期后仍可显示缓存，平台调度器各自决定实际执行时间。读取凭据的连接身份比较与配对账户索引恢复也在共享层，Keychain、Keystore 和系统读取失败的处理仍由宿主承担。

## 存储与安全边界

| 数据 | 存放位置 | 谁能读 | 说明 |
| --- | --- | --- | --- |
| Desktop 配对材料 | 用户私有目录 `pairings-v1.json` | 当前用户的展示 App | 通过 POSIX 权限或 Windows ACL 限制访问，原子提交；未接入系统钥匙串或平台密钥库 |
| 配对秘密 | iPhone 私有 Keychain，`AfterFirstUnlockThisDeviceOnly`，不同步 | 仅主 App | 重启后需解锁一次才能后台认证 |
| 设备 UUID | iPhone 私有 Keychain | 仅主 App | 重装后可从配对账户名恢复唯一身份；多组身份时拒绝猜测 |
| 完整展示缓存、摘要 | App Group | App、小组件 | 不含图片字节、配对秘密、本机路径 |
| 只读 HTTP 目标 | App Group 独立文件 | App、小组件 | 独立 32 字节密钥，只能读摘要 |
| 图片原文件 | iPhone 私有目录，排除备份 | 仅主 App | 通过 Watch 通道逐块转发 |
| Watch 只读配置 | Watch 本机 Keychain | 仅 Watch | 带单调修订号，旧消息不能复活已撤销的配置 |

独立 HTTP 目标会持久化经认证连接得到的地址、端口和只读密钥，供后台刷新使用；“不保存 IP”只适用于主连接配对记录及 Bonjour 后台目标，不能概括为所有存储。只读摘要的加密由 Apple CryptoKit／Android JCA（Java 系统密码接口）执行，不链接 Rust 主连接桥。

其他边界：

- Bonjour 广告的 TXT 只用于展示候选，**不授信**；不接受广告里的 URL 或固定 IP。
- 主连接帧、只读 HTTP 响应、Watch RPC／分块、展示记录与图片缓存各自有容量校验。源图片限制为 16,777,216 像素；Apple 另限制最多 512 帧、iPhone 8 MiB／张、Watch 2 MiB／张的解码预算。Android 沿用系统动图解码，不施加 Apple 的逐帧预算。
- 缓存正式提交采用原子替换，分块先写临时文件并完整校验；受保护的存储路径检查文件类型与符号链接。App Group 的跨进程读改写另使用 `flock` 文件锁，串行 owner 不替代跨进程锁。

## Android 端的差异

- Compose 通用界面现在与 Desktop 共用 `sharedUI/commonMain`；后台设置、系统动效监听、图片视图与本地时间格式仍位于 `androidApp/ui/platform`。`androidApp` 直接依赖 `sharedLogic` 与 `sharedUI`，页面由应用 owner 注入图片与权限动作。
- 网络引擎 `AndroidLanEngine` 在 Kotlin 中实现，同样串行 owner + Rust 桥；发现用 NSD。空闲等待最长 30 秒，命令、发现和生命周期变化会立即唤醒，连接与心跳等期限仍限制等待时间。
- 完整主面板快照只在当前连接内存中，不做离线展示缓存；每次合法实时快照另调用 `AndroidWidgetStore.acceptLive` 持久化裁剪摘要与受保护的只读目标，断线后小组件可以继续展示。摘要是二进制编码，目标单独加密；不能把整个文件概括为加密快照。
- 后台有两种模式：`JobScheduler` 申请 15 分钟周期的只读 HTTP，或用户显式开启的前台服务（常驻通知）保持实时连接。
- 额外提供 Token／Hooks 两页悬浮窗；没有 Watch。服务管理生命周期，`AndroidOverlayWindow` 管理窗口与拖动，`AndroidOverlayPages` 生成内容。权限变化与亮灭屏使用系统回调和广播，不再定时轮询；展示投影未变化时不重建视图，通知只在连接状态变化时更新。

## Desktop 实验展示端

Desktop 与 Android 共用完整展示台和设置，但网络与存储由独立 JVM 宿主管理。`DesktopLanBrowser` 在有效 IPv4 网卡上浏览 mDNS（局域网多播服务发现）；有界 DNS 缓存处理 TTL 到期和服务撤回，广告只作为候选。发现查询目前使用 IPv4 多播，解析器能处理 AAAA 记录，但没有 IPv6 多播通道，未验证 IPv6-only 网络。`DesktopLanEngine` 单线程持有 Selector、socket、Rust 句柄与配对状态，向 AWT 事件线程只投递最新投影；`DesktopHookImage` 在后台解码图片，Compose 负责显示与动画时钟。

现有采集端只接受 Android／iOS 平台。按用户要求，`DesktopPadIdentity` 的加密设备信息发送 `platform: "android"`，仍使用本机真实持久 UUID 与设备名称；只有本连接认证快照广告 `deviceFormFactorV1` 后，才上报一次 `formFactor: "tablet"`。这使采集端把实验终端识别为 Android 平板，无需改动外部采集端源码。

窗口失焦或最小化时仍维持网络会话；最小化和不可见时暂停界面动画，关闭窗口结束引擎。实时完整快照仅在内存，断线即清空。图片经 Rust 完整性校验后原子落盘，必须被新认证快照重新引用才能显示；淘汰沿用共享的 512 MiB／512 文件目标。Skia 支持 BMP、PNG、JPEG、WebP 与 GIF，源图最多 16,777,216 像素、动画最多 512 帧，缩略帧合计目标 8 MiB。

设备身份、名称与面板偏好存 `settings.properties`，配对材料存 `pairings-v1.json`，图片在 `lan-assets-v1/`。配对材料当前使用本用户私有文件，未调用 Keychain／Keystore；POSIX 系统使用 0700 目录和 0600 文件，Windows 使用用户 ACL。Desktop 没有系统小组件、Android 悬浮窗、Watch 通道或独立 HTTP 摘要任务，也不会读取本机 AI 工具凭据或采集用量。

宿主原生库由 `scripts/build_desktop_native.py` 从外部锁定 Rust 工作区与现有 JNI C 包装构建；随当前架构 JAR 分发，启动时解压到私有临时目录后用绝对路径装载。详细构建、存储与实际验证见 [11 Desktop 实验展示终端](11-Desktop实验展示终端.md)。

需求层面的完整对照见 [03 业务需求整理](03-业务需求整理.md)。
