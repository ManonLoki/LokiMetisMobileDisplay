# 02 技术架构

> 上一篇：[01 文件结构](01-文件结构.md) ｜ 下一篇：[03 业务需求整理](03-业务需求整理.md)

本篇以 Apple 端（iPhone、Watch、小组件）为主线，说明数据从桌面到每块屏幕的完整路径，以及支撑它的线程模型、存储划分和安全边界。Android 端结构对等，最后单独说明差异。

## 为什么这样分层

整个系统按“谁最可信、谁最受限”来分工：

| 层 | 承担什么 | 为什么放在这里 |
| --- | --- | --- |
| 桌面（Rust） | 统计 Token、读取额度、产生 Hooks；配对与加密协议的唯一实现 | 数据源头；密码逻辑只写一份，Android 与 iOS 不会各写各的出现分歧 |
| iPhone App | 唯一持有配对秘密；认证、接收完整快照与图片；分发给 Watch 和小组件 | 只有它能长时间运行网络、访问 Keychain、做后台刷新 |
| Watch | 显示、本机缓存；iPhone 不可达时用只读 HTTP 自取摘要 | 算力、电量、网络都最受限，不该持有长期秘密，也不该自己维护 TCP 长连接 |
| 小组件 | 显示最近一次摘要；系统唤醒时短时 HTTP 刷新 | 系统只给几秒执行时间，不能做配对和认证 |

由此得出一条贯穿全局的原则：**能力向下逐级收窄**。iPhone 拿到的是完整权限，Watch 和小组件只拿到“只读摘要”的独立密钥；即使只读密钥泄露，也拿不到配对秘密、Hook 正文或图片。

Apple 端的 Codable 数据编解码、文件事务、网络与 Watch 通道适配放在 `appleDisplay`：Xcode 的 App、Watch、小组件 target 按需直接编译这些 Swift 源码，并分别链接对应平台的 `SharedLogic.framework`。SwiftPM（Swift 包管理工具）测试实际链接 `macosArm64` Kotlin 框架；统一入口 `python3 scripts/test_apple_shared.py` 会先构建框架再执行测试。Swift 侧保留系统适配，共用业务规则由 Kotlin 实现。

## 共享规则与平台实现

当前采用“共享业务规则、保留原生界面”的 KMP 分工。Gradle 模块依赖为 `androidApp → sharedLogic`；iPhone／iPad、Watch 与 iOS 小组件均实际链接 `SharedLogic.framework`。原 `sharedUI` 只有 Android 目标，已合入 `androidApp`，Compose 页面与原生 Android 入口在同一模块内组织。

| 位置 | 当前职责 | 调用范围 |
| --- | --- | --- |
| `sharedLogic/commonMain/domain` | 完整／摘要使用的快照和额度模型、语义校验；面板默认值、配置恢复、列数和分页 | Android 与 Apple 实际调用；Swift 保留 Codable 字段映射，校验交共享模型 |
| `sharedLogic/commonMain/protocol` | 名称与能力校验、连接阶段／期限、最多 8 次退避重试、形态上报、帧容量／长度、写队列、Watch 前台租约／通信事实／传输选择／块边界、JSON 边界、主 LAN／Watch 图片引用与候选、只读 HTTP 请求与响应及局域网地址边界 | Android 与 iPhone 共享主连接规则；Apple 各目标按功能调用 Watch 规则，系统传输与字节缓冲留在平台 |
| `sharedLogic/commonMain/presentation` | Agent 别名、启用过滤、排序、Token／额度行合并、Cursor 默认零行、数字格式化、摘要裁剪、图片解码预算 | Android、iPhone、Watch 与小组件按各自界面调用共享规则；图片系统解码器留在平台 |
| `sharedLogic/commonMain/storage` | 来源与接收时间接纳、同时间完整度优先、历史图片／清除事实、图片淘汰资格与预算、旧 HTTP 拒绝、租约、刷新判断、读取凭据身份比较、配对索引身份恢复、Watch HTTP 配置修订／撤销／去重／缓存保留 | Android 与 Apple 按实际功能在本地锁或文件事务中调用；不包含磁盘或密钥库访问 |
| `sharedLogic/androidMain` | NSD、TCP、Keystore、文件缓存、小组件 HTTP、JNI | 仅 Android；按 `connection`、`storage`、`widget`、`nativebridge`、`protocol` 分目录 |
| `sharedLogic/appleMain` | Foundation Unicode NFC 适配，供各 Apple 目标复用相同的名称比较语义 | 保留原文，只规范化比较键；Android 使用系统 Normalizer |
| `androidApp` | Compose、权限、应用生命周期、前台服务、悬浮窗、系统小组件和刷新调度 | 仅 Android |
| `iosApp` 与 `appleDisplay` | SwiftUI、Network.framework、Keychain、App Group、WatchConnectivity、WidgetKit | 按 Apple target 的权限与生命周期分别执行 |

表中的 `commonMain`、`androidMain` 是源码集合；实际文件在对应集合的 `kotlin/com/manonloki/lokimetrisdisplay/` 下分目录。此次目录分层保留原 Kotlin package，避免改变 JNI 入口及 Swift 导出 API。网络 owner、线程和系统后台资格仍归各平台，不因共用策略而变成同一个跨平台常驻服务。

`TerminalWidgetSnapshot` 从原 Android 摘要类提取到共享层，负责从合法快照裁剪正文、图片与资源清单，以及验证裁剪结果。Apple 保留既有 Codable 摘要和缓存字段，将值映射到共享模型进行校验。Swift 与 Kotlin 的整数转换先检查范围或确保越界值仍被拒绝，非法输入通过结果值或 Swift 自身错误处理，不依靠未声明的 Kotlin 异常跨语言传播。

Android 主面板与 Apple 各界面调用共享的 K/M/B 缩写和精确整数分组；Android 桌面小组件调用同一 `TokenFormatting` 的 K/M/B/T/P/E 入口，保留原有单位策略。共用规则不改变各端原有持久化字段：平台继续负责文件版本、原子提交、密钥库、系统调度和刷新间隔。

展示策略直接通过 `UsageDisplayPolicy` 和快照的 `displayUsageRows` 调用。没有生产消费者的顶层转发与旧展示入口已删除；Swift Codable 外壳和实际使用的 UI／错误适配继续保留，测试覆盖生产投影或共享策略本身。

Apple 摘要存储只保留认证提交、心跳续期和 HTTP 接纳等实际生产入口。旧独立目标写入与无条件摘要写入已移除；测试通过真实认证事务建立状态，专门的进程中断盘面由测试夹具构造，不向生产模块恢复旁路写 API。

Apple 构建目标包含 iOS arm64 真机／arm64 模拟器、watchOS arm64_32 与 arm64 真机／arm64 模拟器；`macosArm64` 用于 Apple Silicon 本机测试。Xcode 各 target 统一调用 `python3 scripts/build_apple_shared.py`，通过进程锁串行构建对应框架。Rust 配对桥只随 Android 与 iPhone／iPad 主 App 构建和链接，Watch、小组件的只读 HTTP 加密使用系统实现。

## 端到端数据流

### 1. 发现与配对（首次）

```
iPhone 前台                                 桌面
  │  NWBrowser 浏览 _loki-host._tcp.local.    │
  │◀──────────── Bonjour 广告（只作候选，不授信）│
  │  用户点“配对” → Rust 开配对窗口，生成四位码 │
  │──── TCP：pairHello ─────────────────────▶│  桌面弹窗，用户输入四位码
  │◀─── reply ───────────────────────────────│
  │──── confirmation ───────────────────────▶│
  │  Rust 返回配对材料 → 写 Keychain → 读回成功 │
  │──── ack（只有 Keychain 真正保存后才发） ──▶│
  │  关闭这条 socket，另开新连接走认证          │
```

配对窗口 60 秒、5 次尝试的预算完全由 Rust 管理；Swift 侧的网络重试不会重开窗口，也不会返还次数。

### 2. 认证与实时同步（之后每次）

```
iPhone                                       桌面
  │── resume introduction（用保存的秘密）───▶│
  │◀── resumeReply ─────────────────────────│
  │── confirmation ────────────────────────▶│
  │── 加密的设备信息（名称、平台、版本）─────▶│
  │◀── snapshot（完整快照）──────────────────│  收到第一份快照才显示“已连接”
  │◀── ping ─▶ pong（桌面定期发送；45 秒没有任何入站消息即判断线）
  │── assetRequest(hash, offset) ──────────▶│  一次只请求一张图的一个 16KiB 块
  │◀── assetChunk ──────────────────────────│
```

主 App 的局域网会话加密、序号和资源完整性检查由 Rust 完成（`NativeLinkBridge.call`）。Swift 按 Rust 给的阶段收发帧，并在任何异常时**关闭 socket 换新连接**——已经消耗的加密序号绝不在同一连接上重发；连接选择与重试预算由共享 Kotlin 策略维护。

`TerminalFramePolicy` 统一长度前缀后的正文边界、单次最多 16KiB 读取与累计缓冲容量；`TerminalWritePolicy` 统一包含在途帧的 8 项写队列和 2 秒写期限。握手帧上限 4096 字节，业务密文帧上限 98304 字节。Android 保留 ByteBuffer／ByteArray，Apple 保留 Data 和系统完成回调，容量判断只传数值，不把大块网络缓冲搬到另一语言。

### 3. 快照到达之后的扇出

```
             ┌─▶ 主线程界面（LanLinkView，内容未变则不投递）
             │
认证快照 ────┼─▶ WidgetSnapshotPublisher ─▶ App Group（摘要 + 完整展示缓存）─▶ 小组件刷新（≥30 秒一次）
             │
             ├─▶ 图片：缓存命中？ ─是─▶ 解码队列 ─▶ 界面
             │                   └否─▶ 逐块下载 → Rust 校验 → 原子落盘 → 解码队列
             │
             └─▶ PhoneWatchBridge ─▶ Watch（快照 + 已落盘图片，逐块确认）
```

快照中的可选 `enabledAgents` 表示桌面设置中完整的 Agent 启用名单，不从用量明细或 Hooks 反推。字段缺失或为 `null` 时兼容旧桌面；空数组表示明确全部关闭。各端按名单生成可见用量行与额度列表，保留桌面给出的总量、质量和时间。名单随 HTTP 摘要、缓存及 Watch 快照传递，避免重启或后台刷新后重新出现已关闭的账户。

### 4. iPhone → Watch

Watch 通道用 `sendMessageData` 即时 RPC 传输快照与图片，不用系统后台文件队列（避免无法撤销的排队传输）。另外通过 `updateApplicationContext` 下发只读 HTTP 配置、缓存撤销标记，以及容量允许时的最近快照缓存；上下文超过 32KiB 时只发送配置与撤销标记，大快照由即时 RPC 分块补齐。

| 操作 | 方向 | 作用 |
| --- | --- | --- |
| `probe` | 手机→表 | 确认 Watch 前台在线，取回其前台代次与已持有的快照摘要 |
| `snapshotBegin` / `snapshotChunk` | 手机→表 | 分块传快照（每块 16KiB，单 RPC 不超过 32KiB，快照总量不超过 96KiB） |
| `assetBegin` / `assetChunk` | 手机→表 | 分块传图片；Watch 已有同摘要文件则直接回复 `cached` |
| `requestSync` | 表→手机 | Watch 主动要最新缓存；手机即使不在前台也能回复 |
| `pause` | 双向 | 通知对方本次前台代次已结束 |

关键约束：

- **单物理槽**：任何时刻只有一个 RPC 在途。超时（8 秒）只撤销逻辑资格，系统回调真正结束前不发第二个，防止系统内部无限排队。
- **先补图，后发新快照**：已提交清单里还缺的图片优先传完，持续变化的用量更新不能把大图“饿死”（共享 `WatchTransferRules`，Swift 保留 `WatchTransferPolicy` 负载枚举映射）。
- **租约**：两端各自记录最近一次真实通信时间，45 秒内才算可达。手机每 15 秒发一次 `probe` 续约，系统的 `isReachable` 只作为“可以尝试”的前提，不作为在线证明。

`WatchCommunicationPolicy` 维护前台代次、45 秒租约、真实 ACK 序号和完整同步事实；普通分块回执只更新通信，不伪造完整同步。报告年龄向上取整到毫秒，超过七天的事实省略。Swift 的 UInt64（64 位无符号整数）纳秒时间通过高低位完整传入共享层，在 Kotlin 内部使用无符号整数比较；状态不可变，复制给另一 owner 的事实快照不会被后续 ACK 修改。`WatchProtocolRules` 负责元信息、RPC 操作／状态及精确块偏移／块长校验，Swift 继续组装原始 Data、核对 SHA-256、编解码 JSON 并调用 WatchConnectivity。

### 5. Watch 的后备路径

```
Watch 前台 / 后台刷新
  │
  ├─ iPhone 可达？──是─▶ requestSync ─▶ 收到缓存或等待分块（最多 8 秒）
  │                                     └─ 超时或无进展 ─┐
  └─ 否 ─────────────────────────────────────────────────┴▶ 只读 HTTP 向桌面取摘要（15 秒内最多一次）
```

HTTP 只返回 Token、额度和 Hooks 四态，不含正文和图片；Watch 会保留同一插槽、同一 Agent 之前已缓存的图片关联。

下发 HTTP 配置的 `WatchConfigurationPolicy` 统一修订接纳、显式撤销、重复消息去重和缓存保留。跨语言边界把修订号表示为规范 u64 十进制字符串，Swift Codable 仍保留 UInt64 字段；同手机只接受更高修订或完全相同的重送，同号内容冲突与旧消息不能恢复撤销授权。新修订先持久提交再发布，u64 耗尽时拒绝递增。规则还决定哪些同手机、同来源的缓存或在途作业可以保留；撤销 HTTP 权限可以保留相容的已验证展示缓存，但缓存不能恢复读取授权。Keychain、配置字节编码及系统发布继续由 Swift 负责。

Android 与 Apple 的只读 HTTP 客户端共同调用 `WidgetHttpPolicy`，统一固定路径、6 秒期限、96KiB 响应容量、响应来源与类型、重定向和 nonce（每次请求的随机值）边界，以及绑定请求 nonce 的附加认证数据。平台继续组装 URL／JSON、执行 Base64 解码和密码运算、按流限制实际字节；Android 原有 1KiB 请求上限与规范 Base64 要求、Apple 原有响应 Base64 接纳方式保留。`WidgetEndpointRules` 共用严格 IPv4、scope（IPv6 接口作用域标识）与已解析地址字节分类；IPv6 解析继续由系统执行，Apple 的 `.local` 与构造时小写化、Android 的数值对端约束保持原样。

### 6. 后台刷新

| 端 | 机制 | 间隔 | 做什么 |
| --- | --- | --- | --- |
| iPhone | `BGAppRefreshTask` | 申请最早 5 分钟后，由系统决定 | 用保存的 Bonjour 服务名重新解析地址，认证，收一份快照写入 App Group 后结束；不下载图片，25 秒本地超时 |
| 小组件 | Timeline `.after(5 分钟)` | 同上 | 若 App 正保持实时连接（摘要在 45 秒租约内）直接读缓存；否则发一次只读 HTTP |
| Watch | `scheduleBackgroundRefresh` | 申请 5 分钟后 | 先读手机上下文与缓存，不可达再 HTTP，12 秒预算 |

## 线程与队列模型

所有可变状态都归属某个 owner，并只在该 owner 的串行队列上读写；主线程只接收不可变的“投影”。这是避免数据竞争、同时保证界面不卡顿的核心约定。

| 队列 | 所属 | 负责 | 不做什么 |
| --- | --- | --- | --- |
| 主线程 | SwiftUI、`LanLinkModel`、`WatchLinkModel` | 渲染、把投影赋给 `@Published` | 不做文件、Keychain、网络、解码 |
| `LokiMetris.lan-link` | `LanLinkEngine` | Bonjour、TCP、Rust 调用、Keychain、图片分块写盘、1 秒期限检查 | 不做多帧解码与冷启动整文件校验 |
| `LokiMetris.lan-decode`（utility） | `LanLinkEngine.decoder` | 图片校验与解码，结果回投网络队列 | 不碰引擎状态 |
| `LokiMetris.phone-watch` | `PhoneWatchBridge` | WCSession 回调、分块传输、配置下发、15 秒心跳 | — |
| `LokiMetris.widget-snapshot` | `WidgetSnapshotPublisher` | App Group 写入（跨进程文件锁）、`reloadTimelines` | — |
| `LokiMetris.watch-link` | `WatchLinkEngine` | WCSession 回调、分块接收、本机缓存、HTTP 结果处理 | 不做解码 |
| `LokiMetris.watch-decode`（utility） | `WatchLinkEngine.decoder` | Watch 图片解码 | 不碰引擎状态 |

**后台 → 主线程的投递**统一用 `LanProjectionDelivery`：只保留最新一份值和最多一个待执行任务，主线程慢的时候中间状态直接被覆盖，不会积压。再加上引擎侧“与上次投递相同则跳过”，心跳、分块回执这类不改变界面的事件完全不会唤醒主线程（见 [04 · 性能优化](04-问题与技术路线.md#四本轮-ioswatch-性能与耗电优化)）。

**迟到回调的处理**：每次重连、切换桌面都递增 `generation`；所有异步回调都带着发起时的代次，回来时不一致就直接丢弃。Watch 侧对应的是 `foregroundGeneration`、`phoneRevision` 和 `httpAttempt`。

## 连接状态机

Android 与 iPhone 使用共享 `TerminalSessionPhase`；iOS 的 `LanLinkEngine.Phase` 是它的类型别名。它描述当前这条 socket 处于协议的哪一步：

```
idle ─(首次配对)─▶ pairHello ─▶ pairConfirmation ─▶ pairClose ─▶ idle ─(另开连接)─┐
  └─(已配对)──────────────────────────────────────────────────────────────────▶ resumeReply ─▶ metadata ─▶ streaming
                                                                                         streaming ─(退后台)─▶ pausing ─▶ idle
```

- `TerminalSessionTimingPolicy` 统一配对 60 秒、握手／首次快照 15 秒、配对收尾 3 秒、入站空闲 45 秒、单块图片 10 秒的预算及到期原因优先级。平台 owner 读取本机单调时钟并执行资源清理；iOS 用 1 秒计时器检查，没有连接也没有期限时挂起。
- 失败分两类：**传输失败**（断网、超时）在新 socket 上有界重试，最多 8 次、退避 0.5～8 秒；**协议／认证失败**不重试，保留配对让用户决定是否忘记后重配。Android 与 iPhone 主 App 共享 `TerminalConnectionPolicy` 的选择与退避规则，调度和 socket 执行分别留在平台 owner。

首次快照的预算起点仍保留两端现状：iOS 沿用 `connect` 开始的握手期限，Android 在认证确认的写入完成回调中重新开始 15 秒预算。共同阶段和预算值不代表这一平台差异已被消除。

`TerminalCapabilities` 共用有界能力表和产品能力名；缺失字段映射为空表，坏类型或畸形表不能授予能力。畸形能力表在两端都会撤销独立 HTTP 读取目标，后台入口仍可缓存其余合法摘要；实时连接入口另按原有严格校验处理。

## 缓存与“谁更新”的判定

iPhone 实时快照、iPhone 后台刷新与小组件 HTTP 摘要写入同一个 App Group 缓存，必须有一致的“新旧”规则，否则旧数据会覆盖新数据。Watch 接收的手机数据和自行获取的 HTTP 摘要写入 Watch 本机缓存，不访问 iPhone 的 App Group。

App Group 缓存按以下规则合并；来源、时间、同时间完整度与 HTTP 接纳判断通过 `SnapshotAcceptancePolicy` 调用共享层，实际加锁、读写和原子替换仍在 Swift：

1. **同一来源才比较**；换桌面直接清空。
2. **按真实接收时间**（`phoneReceivedAtMs`）比较，晚的赢。
3. **时间相同按完整度**：完整快照（优先级 2）> 带历史图片的 HTTP 投影（1）> 纯摘要（0）。
4. **HTTP 只更新状态，不清图**：同一插槽、同一 Agent 的已缓存图片关联继续保留，并记录图片自己的接收时间；插槽换了 Agent 或完整快照明确清图时才移除。

图片字节本身只存在 iPhone 私有目录（按 SHA-256 命名），缓存里只记录清单；每次复用前都会核对长度、格式魔数与摘要。

`HookImageCachePolicy` 维护手机与 Watch 的历史图片选择、清除墓碑（记录插槽图片被明确清空的时间）和完整度优先级。相同手机、相同来源且时间未倒退的摘要才可复用历史图；插槽换 Agent、明确清图或同时间已有清除记录时，旧图片不能重新出现。共享层只处理槽位、Agent、图片摘要及时间等事实，Swift 按决定映射原有 Hook 和资源描述，文件路径与图片字节不进入规则对象。

`AssetTransferRules` 共用主 LAN 与 Watch 的完整描述／引用资格，主 LAN 候选按原清单顺序返回索引。Android 排除已解码与失败图片，iOS 还排除正在异步解码的图片；两端仍在下一块到达后才取消失效资源，各自执行缓存优先查找、解码和网络发送。Watch 图片块与快照块复用有界精确偏移规则，仍分别限制为 32MiB 和 96KiB。

`ImageCachePolicy` 共用受保护文件的排除、按宿主原有访问时间精度排序和容量核算；只有文件实际删除成功才扣除占用。iPhone 继续只按字节预算收敛，Android 与 Watch 同时限制文件数。目录扫描、符号链接检查、文件删除及失败处理仍在平台。

`ImageDecodePolicy` 共用源图片像素边界、目标尺寸及 Apple 逐帧预算与缩边判断。Android 仍使用系统解码器并沿用原有逐图缩放；Apple 仍使用 ImageIO 读取帧信息并核算真实行字节，保留全部动画帧。共享预算不把图片或像素缓冲传入 Kotlin。

摘要的 45 秒租约与是否需要刷新由 `SnapshotFreshnessPolicy` 判断。租约到期后仍可展示缓存，只有当前认证连接的真实通信能续租；平台调度器各自决定实际执行时间。读取凭据的连接身份比较与配对账户索引恢复也在共享层，Keychain、Keystore 和系统读取失败的处理仍由宿主承担。

## 存储与安全边界

| 数据 | 存放位置 | 谁能读 | 说明 |
| --- | --- | --- | --- |
| 配对秘密 | iPhone 私有 Keychain，`AfterFirstUnlockThisDeviceOnly`，不同步 | 仅主 App | 重启后需解锁一次才能后台认证 |
| 设备 UUID | iPhone 私有 Keychain | 仅主 App | 重装后可从配对账户名恢复唯一身份；多组身份时拒绝猜测 |
| 完整展示缓存、摘要 | App Group | App、小组件 | 不含图片字节、配对秘密、本机路径 |
| 只读 HTTP 目标 | App Group 独立文件 | App、小组件 | 独立 32 字节密钥，只能读摘要 |
| 图片原文件 | iPhone 私有目录，排除备份 | 仅主 App | 通过 Watch 通道逐块转发 |
| Watch 只读配置 | Watch 本机 Keychain | 仅 Watch | 带单调修订号，旧消息不能复活已撤销的配置 |

本轮只移动已有业务判断，正文／图片分发范围、配对秘密归属和系统权限没有扩张。

其他边界：

- Bonjour 广告的 TXT 只用于展示候选，**不授信**；不接受广告里的 URL 或固定 IP。
- 所有网络和文件输入在解析前先检查字节上限，图片额外限制像素（16MP）、帧数（512）和解码内存（iPhone 8MiB／张，Watch 2MiB／张）。
- 文件写入一律原子替换，读写前拒绝符号链接；跨进程写 App Group 使用 `flock` 文件锁。

## Android 端的差异

- Compose 界面已从只支持 Android 的 `sharedUI` 合入 `androidApp/ui`，后台设置、系统动效监听、图片视图与本地时间格式位于 `ui/platform`；`androidApp` 直接依赖 `sharedLogic`。Compose 动效本身和系统动效资格有各自职责，保留分文件；页面由应用 owner 注入图片与权限动作。
- 网络引擎 `AndroidLanEngine` 在 Kotlin 中实现，同样串行 owner + Rust 桥；发现用 NSD。空闲等待最长 30 秒，命令、发现和生命周期变化会立即唤醒，连接与心跳等期限仍限制等待时间。
- 完整快照只在当前连接内存中，不做离线展示缓存；小组件只存摘要。
- 后台有两种模式：`JobScheduler` 每 15 分钟只读 HTTP，或用户显式开启的前台服务（常驻通知）保持实时连接。
- 额外提供 Token／Hooks 两页悬浮窗；没有 Watch。服务管理生命周期，`AndroidOverlayWindow` 管理窗口与拖动，`AndroidOverlayPages` 生成内容。权限变化与亮灭屏使用系统回调和广播，不再定时轮询；展示投影未变化时不重建视图，通知只在连接状态变化时更新。

需求层面的完整对照见 [03 业务需求整理](03-业务需求整理.md)。
