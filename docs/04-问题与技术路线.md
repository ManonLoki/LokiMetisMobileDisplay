# 04 解决问题的思路与技术路线

本篇保留 2026-10-22、`v1.0.6` 发布前的 iOS／Watch 排查与清理记录。文中的“本轮”“现在”均指那次改动，测试数量、构建结果和性能推断不代表本次文档核对重新执行的结果。当前分层与源码入口以 [02 技术架构](02-技术架构.md)、[07 当前架构](07-当前架构.md) 为准，最新发布 UI 证据见 [09](09-v1.0.6发布与UI验证.md)。

## 一、贯穿全局的四条思路

这四条原则在下面每个具体问题里都会出现，先放在前面：

1. **一个 owner、一条串行队列。** 网络、Watch 通道、共享写入各自只有一个对象拥有可变状态，所有读写都排在它自己的队列上；主线程只接收不可变投影。同一 owner 的队列内状态不需要额外互斥锁；跨队列完成回调、投影合并和 App Group 跨进程文件事务仍分别使用锁。代价是任何耗时操作都会堵住这条队列，所以耗时的解码要单独放到另一条队列（见第四部分 P3）。
2. **失败就关闭，不在原地修补。** 一条 socket 上任何异常——坏帧、认证失败、半写超时——都直接关掉换新连接，不尝试跳过或重发。加密序号一旦消耗就不能复用，原地重发只会制造更难排查的状态。
3. **在线要有证据。** Bonjour 广告、握手成功、系统的 `isReachable` 都只是“可以尝试”。只有收到第一份真实快照才显示“已连接”；Watch 只有 45 秒内真的收到过回执才算可达。缓存永远带着原始接收时间，读到缓存不等于刷新了数据。
4. **能力向下逐级收窄。** Apple 的主连接配对秘密只在 iPhone／iPad；Android 主 App 独立保存自己的配对秘密。小组件和 Watch 的 HTTP 权限只使用独立的摘要密钥。每往下一层，能做的事更少，泄露后的影响也更小。

## 二、关键问题与技术路线

### 1. 加密序号与网络重试的冲突

**问题**：每条加密消息都有递增序号，发送失败时如果在同一 socket 重发，会和对端的序号对不上；如果跳过，又会留下空洞。

**路线**：重试单位是“整条连接”而不是“一条消息”。`LanSocket` 写队列最多 8 帧、一次只写一帧、2 秒半写超时；任何写失败都关闭连接，由引擎在新 socket 上重新认证。先快速重试 8 次，退避 0.5～8 秒；已配对设备随后每 30 秒继续恢复，首次配对仍保持原传输上限。**网络重试不会重开配对窗口、也不返还四位码的尝试次数**——那份预算完全归 Rust 管。

### 2. 配对“保存成功”到底由谁说了算

**问题**：如果手机先回 ACK 再写 Keychain，写失败时桌面以为配对成功、手机却没有秘密，两边永久不一致。

**路线**：严格按“Rust 给材料 → 写 Keychain → 读回比对 → 告诉 Rust 已保存 → Rust 生成 ACK → 发送”的顺序。Keychain 写失败就不发 ACK。万一出现单边记录（例如手机存了、桌面过期了），用户可以在设置里“忘记此桌面”后重新配对。

### 3. 多个写入源下，哪份缓存更新

**问题**：iPhone 实时快照、iPhone 后台刷新与小组件 HTTP 摘要会在不同进程、不同时间写入同一个 App Group。Watch 另将手机数据和自行获取的 HTTP 摘要写入本机缓存。早期出现过“HTTP 摘要把完整快照里的图片关联冲掉”的问题。

**路线**：统一判定规则（详见 [02 · 缓存判定](02-技术架构.md#缓存与谁更新的判定)）：同来源才比较 → 接收时间晚的赢 → 时间相同时完整快照优先 → HTTP 只更新状态、不清图。每个插槽额外记录“图片接收时间”和“清图时间”，迟到的完整快照可以补图或清图，但不能把较新的 HTTP 状态回退。App Group 的跨进程写入用 `flock` 文件锁，判定与写入在同一把锁内完成。

### 4. 大图如何可靠地传给 Watch

**问题**：图片最大 32MiB，WatchConnectivity 单条消息有容量限制；系统的后台文件传输无法撤销，换桌面后旧图仍可能送达。

**路线**：只用即时 RPC，每块 16KiB、逐块确认偏移；全局只有一个物理 RPC 在途，超时只撤销逻辑资格、等系统真正回调后再发下一个，避免系统内部无限排队。传输顺序上“先补完已提交清单里缺的图，再发新快照”，否则每几秒一次的用量更新会让大图永远传不完。Watch 端每块写入后立即检查偏移和长度，最后整文件校验摘要再原子改名。

### 5. Watch 不依赖手机前台

**问题**：用户抬腕时手机多半在口袋里，App 不在前台，没有实时连接。

**路线**：两条腿走路。① 手机即使在后台，`didReceiveMessageData` 也能被系统唤醒，在系统允许执行时从 App Group 读最新缓存回复 Watch；小快照随回执返回，大快照通过即时 RPC 分块补齐。`applicationContext` 另行下发只读配置、缓存撤销标记和容量允许时的快照缓存，超过 32KiB 时只发送配置与撤销标记。② 手机不可达时，Watch 用手机预先下发的**只读 HTTP 配置**直接向桌面取摘要并保存到 Watch 本机缓存。配置带只增不减的修订号（先写入 Keychain 再发布），旧消息无法复活已被撤销的授权。

### 6. 后台任务的完成回调只能调一次

**问题**：`BGAppRefreshTask` 的正常完成、系统到期、新任务替换旧任务三者可能同时发生；回调调两次会崩溃，不调会被系统扣减后台预算。

**路线**：`RefreshExecution` 用锁保护 `completed`、`expired`、`awaitingCleanup` 三个标志，所有路径都经过同一个 `complete(success:)`。替换旧任务时先等网络 owner 清理完旧连接，再以失败结束旧任务。

### 7. 动图的内存与唤醒

**问题**：一个 512 帧的 GIF 如果每帧按原尺寸解码，内存会爆；用固定 60Hz 计时器播放又会持续耗电。

**路线**：解码时按“总预算 ÷ 帧数”给每帧分配边长（iPhone 每张总共 8MiB、最长边 512 像素；Watch 2MiB、256 像素），所有帧共享同一边长，避免重复超限解码。播放器只在“下一帧到来时”睡醒，帧间隔多长就睡多久（最快 60Hz）；不可见、切页、后台、减弱动态效果或 Watch 低亮度时直接结束播放任务，不再唤醒。

### 8. 其他值得记住的坑

- **IPv4 地址带接口后缀**：`NWEndpoint` 的 IPv4 描述可能是 `192.168.1.5%en0`，直接存为 HTTP 目标会校验失败。现在 IPv4 用原始 4 字节重新拼出规范地址，IPv6 保留作用域。
- **挂起的 DispatchSource 不能直接释放**：引擎的 1 秒计时器在空闲时挂起以省电，`deinit` 里必须先 `resume` 再 `cancel`，否则崩溃。
- **iPad 多窗口**：用 App 级 `scenePhase`（汇总所有窗口）控制连接，单个窗口失焦不会断掉另一个仍在前台的窗口。

## 三、排查性能问题的方法

本轮排查没有依赖“感觉”，而是沿三条线逐个检查：

1. **主线程被唤醒多少次**：找出所有 `publish()`／`@Published` 赋值的触发点，统计每个事件（心跳、分块回执、探测）会不会导致整页 SwiftUI 重算。
2. **串行队列上有没有慢操作**：逐个看网络队列、Watch 队列上执行的代码，标出文件读取、哈希、解码、Keychain 访问，估算最坏耗时。
3. **哪些工作在重复做**：同一份文件是否被反复整读哈希，同一份数据是否被多个进程重复从网络取。

## 四、本轮 iOS／Watch 性能与耗电优化

### 问题清单与处理

| 编号 | 位置 | 问题 | 影响 | 处理 |
| --- | --- | --- | --- | --- |
| P1 | `LanLinkEngine.publish`、`PhoneWatchBridge` | 引擎每次 `publish` 都把整个 `LanLinkView` 投给主线程，`@Published` 无条件触发整页重算（`TabView` 中展示台和设置页都存活）。Watch 通道每 15 秒心跳、每个分块回执都会触发；Watch 通信事实（序号、时间）随每次回执变化，也被放进了界面投影 | 连接期间主线程持续被无意义唤醒，耗电、滚动时可能掉帧 | `LanLinkView` 及其子结构改为 `Equatable`，引擎侧记住上次投递值，相同则跳过；通信事实移出界面投影单独交给引擎上报桌面；删除界面从未使用的 `lastContact` |
| P2 | `WatchLinkEngine.receive` | Watch 每收到一个 16KiB 分块都 `publish`，32MiB 的图约 2000 次整页重绘 | 传图期间 Watch 主线程持续忙碌，明显耗电、可能卡顿 | `WatchLinkView` 改为 `Equatable`，内容未变不投递 |
| P3 | `LanLinkEngine+Display` | 多帧图片解码在网络串行队列上同步执行；回前台时 `restoreCachedDisplay` 会先同步读入每张缓存图（最大 32MiB）、调用 Rust 算 SHA-256、再解码全部帧，**之后才开始 Bonjour 发现**；为了校验还专门创建一个 Rust 会话句柄 | 回前台后发现与重连被推迟，连接中心跳回复和图片分块被解码阻塞 | 新增 `LokiMetris.lan-decode` 解码队列（utility 优先级、串行以限制内存峰值）；冷启动的校验和解码全部移过去，结果回网络队列后仅在仍被引用时展示；校验函数本就不需要会话句柄，改为静态调用，不再创建临时句柄 |
| P4 | `IOSDisplayCache.assetPaths` | Watch 每次 `requestSync`（抬腕、每 5 分钟、手机推送缺图时）都把引用的每张图完整读入内存重新算 SHA-256，最坏 12 × 32MiB | 手机端持续的 CPU 与内存开销，即使在后台被唤醒时也会发生 | 按文件系统身份（`fileResourceIdentifier`）记住已校验结果；生产缓存通过原子替换提交，校验结果按文件系统身份复用，避免同一文件重复哈希；记录只保留当前引用的图片 |
| P5 | `IOSAssetCache`、`IOSDisplayCache` | 校验时用 `Data(contentsOf:)` 把整个文件复制到堆上 | 每次校验一张大图就有 32MiB 级的瞬时内存峰值 | 改为 `.mappedIfSafe` 映射读取 |
| P6 | `CyberMotion.swift` | 全屏背景 `Canvas` 以 24 帧／秒重画两层径向渐变，并且每帧重画整张静态网格；卡片边框扫光同样 24 帧／秒 | 展示台在前台时 GPU／主线程持续工作，是“放在桌边当副屏”场景下最大的耗电来源之一 | 将背景光晕刷新降到 8 帧／秒，静态网格拆成 `Shape`，不再按动画时钟重画；扫光每 8 秒一圈，降到 15 帧／秒，每帧约转 3° |
| P7 | `LokiMetrisWidgets.getTimeline` | 当时组件 Timeline 即使已有刚写入的认证摘要，仍会再发一次 HTTP 连桌面 | 额外的扩展进程启动与局域网请求 | 摘要在 45 秒租约内时直接读缓存，不发 HTTP；该租约也可来自刚完成的 HTTP，不作为 App 在线证明 |
| P8 | `WatchLinkEngine.drainConnectivity` | Watch 处理后台配套任务时每 0.2 秒轮询一次是否还有待收内容 | 后台窗口内多余的 CPU 唤醒 | 改为 1 秒（12 秒窗口内最多约 12 次检查，原来约 60 次） |
| P9 | `WidgetDisplayState` | 每次共享写入都发布一个界面从不读取的 `snapshot`，并无条件赋值 `sharingError` | 额外的主线程重算 | 删除无用字段；结果没变不赋值 |
| P10 | `LanLinkEngine.setActive` | 每次回前台都做一次旧快照迁移（建目录、设属性、删文件），并逐条读取全部配对秘密检查 Keychain 可访问性 | 回前台路径上的同步文件与 Keychain I/O | 两段迁移已无必要，整体删除（见第五部分） |

### 评估后保留的设计

不是所有周期性工作都应该删掉，以下几项评估后保留，并写明原因：

| 项目 | 保留原因 |
| --- | --- |
| 手机每 15 秒向 Watch 发一次 `probe` | Watch 可达性靠 45 秒租约证明；15 秒间隔给超时（8 秒）和偶发丢包留了余量。只在手机连着桌面且 Watch App 在前台时发生 |
| 连接期间 1 秒一次的期限检查 | 覆盖配对、握手、心跳、单块图片四类超时；空闲时已挂起计时器 |
| 每次桌面心跳续写 App Group 摘要 | 文件约 1KB，在后台串行队列写入；保证小组件看到的 45 秒租约准确，P7 的跳过逻辑也依赖它 |
| Watch 根视图旧 `TimelineView(.everyMinute)` | 当时为 frontmost inactive 可见性保留；当前 `WatchRootView` 已改为三页布局，无该定时视图，此项仅记历史 |
| 网络队列上首次命中缓存时的同步校验（`nextAsset`） | 每张图每次连接最多一次；改成异步需要重排下载调度，收益小于复杂度 |

## 六、2026-10-23 已配对设备重连修复

本次排查“更换网络或再次打开后无法连接，重启偶尔恢复”。修复最初在 `codex/desktop-experimental` 完成，随后只把共享层、Android 与 iOS 部分重新提交到 `main`；Desktop 实现不随之合入。代码和自动化回归确认以下恢复路径存在缺口；实际 Wi-Fi 切换仍需真机验收。

| 位置 | 原因 | 修复 |
| --- | --- | --- |
| 共享 `TerminalConnectionPolicy` | 同一端点的 8 次重试耗尽后停止；网络稍晚恢复时可能没有新的发现事件来续预算 | 保留 8 次快速退避；已有配对随后每 30 秒继续恢复。首次配对仍有界，协议或认证失败不预约自动重试 |
| Android 发现与连接 | 没有局域网拓扑监视；已有浏览器的 `start()` 不刷新注册；已选地址变化时仍可能保留旧 TCP；发现或服务监听失败后缺少恢复 | 观察 Wi-Fi／以太网地址与路由，切网重建 NSD（系统服务发现）并撤销旧连接；显式重试和无连接时回前台重新浏览；新端点替换旧连接；发现失败和监听注册失败自动重试 |
| iOS 发现与连接 | `NWBrowser.failed` 后不再启动；切网没有主动刷新；在广告校验前取消重连可被非法或重复身份广告打断 | 浏览失败退避重建，前台监视网络路径，手动重试重新浏览；只在候选校验后判断端点更新；缺少端点时继续预约恢复，旧重试带身份检查 |

配对秘密及设备身份沿用原存储。网络恢复只建立新的 TCP 认证会话，不重新生成配对码，也不返还 Rust 密码尝试次数。iOS 的健康连接不因普通路径通知被主动断开；连接失效后由网络错误或原有心跳期限触发恢复。

Android 12 的旧 NSD 接口没有解析取消原语，仍等待唯一系统解析请求的终态回调；不把系统自身永不回调的问题宣称为已解决。支持 `stopServiceResolution` 的系统在停止浏览或解析超时时精确取消旧请求，收到终态后再解析下一项。
